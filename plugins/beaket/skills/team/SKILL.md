# Beaket team

A Beaket team shares decision records among its members. A record is encrypted on the member's machine with a key only the team has, and Beaket keeps the ciphertext. Each member has their own key; managers invite and remove members. A machine can be in several teams, one key pair each, and the folder chooses the team: a repository names its team in `.beaket/team`, and a session reads and shares with that team only after the person trusted that file there (`team use`). No file, or one changed since, means no team: nothing is shown and nothing is shared. Your job is to set the team up, share only what the person chose, and answer questions about it from the code, not from memory.

The script is `node <skill>/scripts/beaket.mjs`, where `<skill>` is this skill's folder, the one that holds this SKILL.md. Use that path in every command and show it to the person when they ask. Run the script on its own, never chained with other commands by `;`, `&&` or `|` nor run from another folder with `cd`, so that a permission that allows the script covers it.

## Rules
- Share a record only when the person said to, by name or as a list they confirmed. Never share a record marked `<!-- beaket-private -->`, one the person said to keep to themselves, or one holding something they said not to share; the script refuses the marked ones.
- An invite code opens the team's key for one person, once, within a day. Keep it out of this conversation, which goes to the model: never run `team invite --print`, never read `team.json` or the `join-code` file, and never ask the person to paste a code here. The script puts it on their clipboard and in a file only they can read; they send it to that one person in a private message. If they paste one here anyway, use it, and say in one line that it went to the model and next time they only need to copy it.
- Answer what Beaket stores or can read only from the plugin's code and README, quoting the lines, and say what you could not check.

## What leaves the machine
When the person asks, read `<skill>/scripts/beaket.mjs`, which is the whole client, and show them:
- The plugin has one script: `bin/beaket.mjs`, and a copy of it in each skill's `scripts/`. `verify` prints its SHA-256 and whether every copy is the same; run it rather than comparing them yourself.
- The decision-brief and decision-record skills read sources through the person's own connectors. What they read goes to the model as in any Claude Code session; the plugin sends none of it to Beaket and has no connector or server of its own for sources.
- In a team, a record goes to Beaket only through `push`, encrypted first with the team key (`sealRecord`); Beaket receives the ciphertext, the nonce and the key's epoch. Each member has their own X25519 key pair and token (`keyPair`); Beaket receives the public key and the SHA-256 of the token, and the team key only wrapped to each member's public key (`wrap`).
- Beaket sees the team's id, each member's random id, role, public key and dates, each record's random id, size, epoch and when it changed, and a log of which member id joined, shared, pulled, withdrew, answered or removed what; like any web server, it sees the IP address of each call. It does not see members' names (sealed on each member's card), a record's title, text or file name, or any key.
- Of each shared record Beaket also keeps a passport (`passportOf`, sent by `push`): its Date, Review by, state (valid, questioned, changed, withdrawn) and who answered what about it and when (`answer`) in the clear; its Label line (two or three words), the name on its Decided by line and the links under Sources, Rests on and Supersedes sealed with the team key, so that Beaket cannot read them (beaket/beaket#3196). This is what agents, the map and other tools read without the text. `passports` shows the team's passports, opened on this machine. A record without a Label line gets the words of its file name.
- The window (`mcp`) is an MCP server on this machine, over standard input and output, through which another AI the person runs here asks for this folder's team's passports and links; it gets no record's text and cannot change anything. It runs with the person's own keys, so it needs no read key, and nothing of it goes through Beaket but the pull of the passports.
- Each person's private key, token and the team keys, one set per team, are in `team.json`, with the hash of each `.beaket/team` file they trusted, and an invite code in `join-code`, both in the config folder `paths` names and readable only by their owner; the records of the last pull are kept sealed in the cache folder `pull` names, one folder per team, with a key derived from the person's private key, and are opened only by `read` and `search`.
- Never write or edit `.beaket/team` yourself: `team use` writes it, and a file the person did not trust with `team use`, or that changed since, is refused by every command. When a command says the file is not trusted, show the person which team it names and ask whether that is right before running `team use`.
- Removing a member (`team remove`): Beaket refuses them at once, and records pushed afterwards use a new key that only those who stay have; the person removed keeps the copies they already pulled. For the records pushed before, the team relies on Beaket's refusal.
- The server: `stg.beaket.com` is Beaket's beta server, and Beaket will run on beaket.com later. Neither the plugin nor its README says how long the beta keeps records or whether beta teams move to beaket.com; say that you could not find it rather than guess.

## Steps
1. **Where they are.** Run `status`, alone; it prints this folder's team, or why there is none (no `.beaket/team`, a file not trusted, a team this machine is not in, or no team at all), and every other team the machine is in.
2. **Make a team** (`team create`) when they ask for one; they become its manager. Then, in the repository that uses it, `team use <team id>` writes `.beaket/team`; tell them to commit it, so that every clone and every teammate uses the same team. It shows the server it used; if it is not the one they expect, say so. If it is `stg.beaket.com`, say in one line that it is Beaket's beta server and that Beaket will run on beaket.com later. A team has no name on Beaket; if they give one, say so.
3. **Invite someone** (`team invite`, or `team invite --manager` for someone who will also invite and remove): one invite per person. Tell them the code is on their clipboard and in the file the script names, that it lets one person join, once, within a day, and that they send it to that person in a private message; that person copies it and asks Claude to join. Only a manager can invite; if the script says so, tell them to ask a manager.
4. **Join a team**: ask them to copy the code their teammate sent, then run `team join`, which reads it from the clipboard (or `team join --file <file>` if they saved it to a file). The machine can be in other teams too; nothing is left. Then `team use` in the repository: with the team id when the repository has no `.beaket/team` yet, alone to trust the one a teammate committed. To leave a team on this machine, `team leave <team id>` (its keys and cached records go; Beaket still lists them until a manager removes them). A code starting with `bkt1.` is from the old shared-code teams: they need a new invite.
5. **Share what is already written.** After making or joining a team, or when asked, run `unshared` in the repository root (or with the folder the person named). It lists each record as shared, not shared or private. Show the not-shared ones by title and ask which to share; share only those (`push <file>...`). Mention the private ones as staying on this machine.
6. **Withdraw a record** (`remove <file>`): it disappears from every member's next pull. Say that members who already pulled it had a copy.
7. **Who is in the team, and who did what**: `team members` lists names, roles and dates; `team log` shows who joined, shared, pulled, withdrew and removed what, and when (`--all` for all of it). Show what they asked about, not the whole log. A member whose card does not match its key is marked by the script; say so plainly.
8. **Remove a member** (someone left, or their laptop was lost): confirm the name with them, then run `team remove <name>` (managers only). Say that Beaket refuses that person from now on, that records shared from now on use a new key they do not have, that unused invites were cancelled, and that they keep the copies they already pulled. Nobody else needs to do anything.
9. **Let another AI ask about the team's decisions** (Cursor, another Claude Code, any tool on this machine that takes an MCP server): give them the command to add as a local MCP server, `node <skill>/scripts/beaket.mjs mcp`, run from the repository whose team it asks about. Say that it reads only passports and links, never a record's text, can change nothing, and works only on this machine with their keys; that what it reads goes to that tool's model. A tool that runs elsewhere (Rovo, a Notion agent) cannot reach it, since Beaket's server can no longer read the passports (beaket/beaket#3196).
10. **Add a question to a record**, someone else's included, when the person wants a question kept with it (for example "note my question so it comes up when this is revisited"): show the line, then after they confirm, append `- <YYYY-MM-DD> <their name>: <question>` under a `## Questions` heading at the end of the record's file (in `decisions/`, or in the team's cache folder for a record only the team has), change nothing else in it, and `push` that file.
11. Say what you ran and what changed, in one or two lines.
